# Everything to bits — the build

One page, one command. The reader receives a single self-contained
HTML file; this directory is where that file comes from, and the
canvas is build output: never edit it by hand.

The project is five files, all in one directory, no dependencies
beyond Python 3 (no Node, no packages, no network):

```
deck.xsd       the single source of truth: what the data may be
deck.xml       the data: icons, primers, placeholders, cards, trails,
               ladder, rails, pattern — prose and doors, no diagrams
template.html  the page skeleton: prose, CSS, JS, the live figures
build.py       validate → test → build (and --install the canvas)
build.sh       the one command: validate, test, build, install
```

`out/site.html` is regenerated by every build. This project is
exported as artifacts (deck.xsd, deck.xml, template.html, build.py,
build.sh, this file). The working environment can be reset between
sessions; the artifacts are the durable copies. To resume work, copy
those six files into one directory and run `bash build.sh`.

## Commands

```
python3 build.py        # validate + test + build out/site.html
python3 build.py --install   # also write the canvas
bash build.sh           # the same, one command
```

Every check must pass before anything is written. A failure prints
every problem found at the failing stage, writes nothing, and exits
non-zero (`1` a check failed, `2` bad usage). On success the build
prints how many checks passed and what the page holds.

## How the build works

`build.py` runs five stages, in order:

1. **parse** — the three files exist, and deck.xml is well-formed
   XML. A syntax error names the line and column.
2. **schema** — the data satisfies deck.xsd, checked by a small
   XSD interpreter carried inside build.py (the environment offers
   no XSD tooling). The schema pins the layers (`level="0"` cards,
   `"1"` trails and placeholders, `"2"` primers), the id patterns,
   the required attributes, the element order. Anything outside the
   interpreter's subset fails loudly rather than passing silently.
3. **data checks** — what the schema cannot express: door targets
   exist, icons and rungs are known, a card's doors never skip
   straight to a primer, every part and step offers at least two
   distinct doors, every pattern row shows at least two orbs, every
   named placeholder is referenced by something, and the template
   carries a section for every view the data names.
4. **build** — the JSON form of the data replaces the template's
   `/*__DECK_DATA__*/{}` slot.
5. **output checks** — the built page itself: the slot was filled,
   the title and every view survived, the tags balance, the payload
   is valid JSON.

The checks are few on purpose. Each guards a mistake that has
actually happened in this project, and each failure names the exact
row and target involved — copy any message into your notes and the
fix is usually obvious.

## Authoring

- **Deck content lives in deck.xml.** A part, a step, a rung: an
  element with its attributes, a `<blurb>`, and `<door>` children.
  Prose needs no escaping beyond `&lt;` for `<` and `&amp;` for
  `&`. There are no diagrams: a part, a step, a rung is prose and
  doors, nothing else. The schema documents the exact shape.
- **The deck is layered, and the layers are data.** Cards carry
  `level="0"`, trails `"1"`, primers `"2"`; the schema pins each
  value. From a card (or its bottom) a door may lead to a trail, a
  placeholder, or another card — never straight to a primer. Trails
  sit one layer down and may reach the primers; that is what they
  are for.
- **Never an anonymous gap.** Where a path is still to come, point
  the door at a named `<placeholder>` and declare it under
  `<placeholders>`: an id, a level, an icon, a title, one line. It
  renders as a grey orb with its own name and icon. Every
  placeholder must be referenced by at least one door, and every row
  must offer at least two distinct doors; the build enforces both.
- **Fleshing a placeholder out** = writing the trail (or primer) it
  promises, deleting the placeholder, and re-pointing its doors at
  the new view.
- **Adding a card** = a `<card>` element with rung-tagged parts, the
  section and spine in template.html (`id="the-card"`,
  `id="the-card-parts"`), and doors from the paths that raise its
  question. The orbs, the pattern's lateral doors, and the ladder
  ordering assemble themselves. **Adding a trail** is one element;
  trails are built at runtime and need no template anchor. **Adding
  a primer** needs a section and at least one `data-go` door to it.
- **The live figures** (the interactive engines inside the primers)
  live in template.html, not the data. The build checks the page
  around them; it does not drive them. Exercise them by hand after
  changing them.

## When the build refuses you

Examples of what a mistake actually prints (paraphrased):

```
BUILD FAILED at schema validation (deck.xsd):
  /deck/cards[1]/card[1]/part[1]: unexpected element <art> (this
  deck carries no ASCII art — delete the <art> element; a part, a
  step, a rung is prose and doors, nothing else)
  nothing was written.

BUILD FAILED at data checks:
  card games, part 1 (the controller): door to 'bits' jolts straight
  to level 2 — ease down through a trail or a named placeholder
  nothing was written.

BUILD FAILED at data checks:
  placeholder p-memory (how it remembers) is never referenced — a
  promise nothing points at
  nothing was written.
```

The schema's error messages carry hints for the shapes that have
bitten before: pasting an `<art>` element back, confusing the
ladder's children (`<rung>` inside `<ladder>`, `<rail>` inside
`<rails>`), and off-pinned levels.

## Why the XSD interpreter

The environment offers no `xmllint`, no Java, no `lxml`, and package
installation is not allowed. Rather than let deck.xsd rot into
documentation the build merely hopes to follow, build.py carries a
small interpreter for exactly the subset the schema uses. The schema
stays the single source of truth: edit deck.xsd first when the
data's shape must grow, and the interpreter will tell you if it
cannot check a new construct.
